# دعم macOS native وسهولة التثبيت — وثيقة التصميم

## النية والسبب

تحويل `sites-dashboard` من أداة تعتمد على Ubuntu/Debian إلى أداة تدعم Linux وmacOS native، مع الحفاظ على تجربة CLI/TUI الحالية وتقديم مسار تثبيت مناسب لمستخدمي Mac. الهدف أن يستطيع المطور تثبيت الأداة وتشغيل أول موقع محلي بدون معرفة تفاصيل `apt` أو `systemd` أو مسارات Homebrew.

## الأهداف

- دعم macOS على Apple Silicon وIntel.
- إبقاء دعم Linux الحالي عاملًا بدون تغيير سلوك الأوامر الموجودة.
- اكتشاف المنصة، معمارية الجهاز، وإصدارات PHP/Homebrew تلقائيًا.
- استخدام Homebrew لتثبيت Nginx وPHP-FPM وMariaDB وMailpit وmkcert والاعتماديات المطلوبة.
- استبدال افتراضات Linux الصريحة بطبقة منصة واحدة مسؤولة عن المسارات، الخدمات، المستخدم، ومشغّل الصلاحيات.
- توفير مثبت واحد يكتشف النظام ويشرح ما يفعله، مع إمكانية إعادة تشغيله بأمان.
- دعم التحقق الآلي الأساسي لمسار التثبيت والإعداد على كل منصة.
- تحديث README ونسخ التوزيع والإزالة والترقية بوضوح.

## ما لن يشمله الإصدار الأول

- لا يوجد Docker backend في الإصدار الأول.
- لا توجد واجهة رسومية جديدة؛ ستظل الواجهة TUI والـ CLI كما هما.
- لا نعيد تصميم نموذج المواقع أو النسخ الاحتياطية أو WordPress.
- لا نعد بدعم Windows في هذا المشروع.
- لا نضمن إدارة عدة إصدارات PHP في نفس الوقت؛ نختار إصدارًا نشطًا واحدًا ونكتشفه.
- لا يتم تشغيل `sudo` بلا كلمة مرور تلقائيًا أو تعديل sudoers.

## ما سيعد فشلًا حتى لو عمل تقنيًا

- أن يضيف دعم Mac شروطًا متفرقة داخل كل أمر ويصبح إصلاح Linux أصعب.
- أن يكتب المثبت إعدادات دائمة فوق اختيارات المستخدم أو يترك خدمات نصف مهيأة بعد فشل جزئي.
- أن يفترض مسارًا واحدًا لـ Homebrew، فيفشل على Intel أو عند استخدام prefix مخصص.
- أن يعتمد إنشاء الموقع على مستخدم Linux مثل `www-data` أو على `systemctl`.
- أن تكون رسالة الخطأ غير قابلة للتنفيذ عندما تكون Homebrew أو خدمة مطلوبة ناقصة.

## القيود الحالية المهمة

- منطق الأداة موجود أساسًا في `bin/sites`، والمثبت في `install.sh`، ومساعد إنشاء المواقع في `bin/newsite`.
- الكود الحالي يثبت مسارات Linux مثل `/etc/nginx/sites-available` و`/run/php/...` ويستخدم `systemctl` و`www-data` و`apt-get`.
- ملف `.deb` مناسب لـ Debian فقط وسيظل مسار توزيع Linux مستقلًا.
- ملفات إعداد Nginx الحالية تُكتب إلى مسارات النظام وتحتاج سياسة مختلفة على macOS.
- `cli_start`, `cli_stop`, و`cli_restart` تحتوي أسماء خدمات PHP ثابتة وتحتاج الاعتماد على معلومات المنصة المكتشفة.
- `cli_create` يفترض أن `newsite` موجود في `~/.local/bin` بينما الباكج يضعه في `/usr/local/bin`؛ يجب توحيد اكتشاف executable أثناء إعادة الهيكلة.

## القرارات المؤكدة

- نطاق macOS هو macOS 13 أو أحدث، مع دعم Apple Silicon وIntel.
- عند غياب Homebrew، يطلب المثبت موافقة واضحة قبل تشغيل المثبت الرسمي؛ وفي الوضع غير التفاعلي يتوقف برسالة تعليمات بدل التثبيت الصامت.
- تعمل خدمات Homebrew بحساب المستخدم الحالي عبر `brew services`، ولا يُستخدم `www-data` على macOS.
- نحافظ على عناوين المواقع الحالية على المنافذ 80/443، مع طلب صلاحية مرة واحدة؛ إذا كان المنفذ مستخدمًا أو غير متاح يظهر خطأ واضح ولا يحدث fallback صامت إلى منفذ آخر.
- تبقى المواقع والنسخ والشهادات داخل مجلدات المستخدم وتستمر عبر الترقية، ولا تحذف إزالة الأداة بيانات المواقع افتراضيًا.
- ندعم التثبيت الجديد والترقية من النسخة الحالية، ولا نعتبر نقل بيئة Linux كاملة إلى Mac ضمن الإصدار الأول.
- يختار النظام PHP تلقائيًا، مع override عبر `SITES_PHP_SERVICE` عند وجود أكثر من إصدار.
- يحدّث المثبت ملفات `.zprofile` و`.zshrc` عند الحاجة بطريقة idempotent، ولا يكرر الأسطر الموجودة.
- `start` و`restart` يديران خدمات persistent عبر Homebrew لتبقى متاحة بعد إعادة تشغيل الجهاز.

## البدائل المدروسة

### البديل A — Native عبر Homebrew (المختار)

نضيف طبقة `Platform`/`ServiceManager` تحدد:

- مسارات Nginx وPHP وملفات الإعداد.
- اسم ومشغل الخدمات (`systemctl` على Linux و`brew services` على macOS).
- طريقة تنفيذ العمليات التي تحتاج صلاحيات.
- المستخدم والمجموعة المناسبين للملفات.
- binary paths وprefix الخاص بـ Homebrew.

يبقى منطق المواقع والنسخ الاحتياطي وWordPress مشتركًا فوق هذه الطبقة. يستخدم المثبت Homebrew على macOS وapt على Debian/Ubuntu. هذا أقل تغييرًا على تجربة الأداة الحالية وأفضل أداءً للمطورين.

### البديل B — Docker

يضع Nginx وPHP وMariaDB وMailpit داخل containers موحدة. هذا يقلل فروق الأنظمة، لكنه يغيّر إدارة الملفات والخدمات والصلاحيات ويضيف Docker Desktop كاعتماد ثقيل. لا يناسب الحفاظ على طبيعة الأداة الحالية كمدير خدمات محلية.

### البديل C — Native أولًا مع Docker لاحقًا

ننفذ A الآن مع تصميم لا يمنع B لاحقًا. هذا هو المسار المختار: لا نبني Docker الآن، لكن نعزل مدير الخدمات بحيث يمكن إضافة backend آخر مستقبلاً.

## التصميم المختار

### طبقة المنصة

نضيف وحدة صغيرة مسؤولة عن قيم التشغيل المكتشفة بدل قراءة المسارات وأسماء الخدمات من أماكن كثيرة. الواجهة المنطقية المقترحة تشمل:

- `platform_name()` و`is_macos()` و`is_linux()` للتحقق الواضح.
- `detect_homebrew()` و`brew_prefix()` لاكتشاف `/opt/homebrew` أو `/usr/local` أو prefix مخصص.
- `detect_php()` لإرجاع socket وservice وbinary الفعليين.
- `nginx_paths()` لإرجاع مجلدي available/enabled.
- `service_action(service, action)` لتوحيد start/stop/restart/status/enable.
- `run_privileged(cmd)` لتوحيد `sudo` مع رسائل فشل مفيدة.
- `runtime_user()` و`runtime_group()` و`site_owner()` لعمليات الصلاحيات.

القيم الافتراضية تظل قابلة للتخصيص عبر متغيرات البيئة الحالية، وتضاف متغيرات قليلة فقط عند الحاجة، مثل `SITES_BREW_PREFIX` و`SITES_PHP_SERVICE` و`SITES_NGINX_PREFIX`.

### macOS installation flow

1. يتحقق المثبت من macOS ومن وجود Homebrew.
2. إذا لم يوجد Homebrew، يشرح للمستخدم سبب الحاجة إليه ويعرض خيار التثبيت التفاعلي؛ لا يثبت برامج خارجية بصمت.
3. يثبت أو يتحقق من `python`, `nginx`, `php`, `mariadb`, `curl`, `wget`, `mkcert`, `mailpit` والاعتماديات اللازمة.
4. يثبت Python packages في virtual environment مملوك للأداة بدل الاعتماد على pip system-wide.
5. ينسخ `sites` و`newsite` إلى مسار ثابت قابل للاكتشاف، ويضيفه إلى PATH عند الحاجة بطريقة idempotent.
6. يشغل الخدمات عبر `brew services` ويجرب readiness checks لـ Nginx وPHP-FPM وMariaDB وMailpit.
7. يكتب ملف إعداد قابل لإعادة القراءة، بدل تكرار اكتشاف المسارات في كل تشغيل.
8. يطبع ملخصًا يتضمن أوامر التشغيل، مسارات المواقع، رابط Mailpit، وأي خطوة يدوية متبقية.

### الملفات والإعدادات على macOS

- يكتشف `brew --prefix` بدل افتراض `/opt/homebrew` فقط.
- يضع إعدادات Nginx الخاصة بالأداة في prefix مناسب تديره الأداة، أو يستخدم مسارًا يحدده المستخدم، مع تجنب الكتابة العشوائية في ملفات Homebrew الأساسية.
- يضيف domains المحلية إلى `/etc/hosts` فقط عند إنشاء موقع، مع عملية قابلة للتكرار ولا تكرر السطر.
- يستخدم مستخدم macOS الحالي لملكية ملفات المواقع، ويستخدم مجموعة النظام المناسبة فقط عند الحاجة.
- يولد شهادات `mkcert` في مجلد بيانات واضح لكل موقع، بدل ربطها بمجلد HOME بشكل غير موثق.

### التوافق مع الأوامر الحالية

الأوامر الحالية (`list`, `services`, `start`, `stop`, `restart`, `create`, `backup`, `restore`, `ssl`, `export`, `dashboard`) تظل بنفس الأسماء. التغيير الداخلي فقط هو أن كل أمر يستدعي طبقة المنصة بدل استدعاء Linux command أو path مباشرة.

### التوزيع والتثبيت

الإصدار الأول يدعم مسارين:

- Linux: `.deb` الحالي + `install.sh` بعد تنظيفه من الافتراضات غير العامة.
- macOS: `install.sh` مخصص للـ native مع خيار نشر Homebrew Tap لاحقًا كمسار مفضل.

بعد استقرار النسخة، يصبح مسار التثبيت المفضل على macOS:

```bash
brew tap <owner>/sites-dashboard
brew install sites-dashboard
```

ويظل السكربت المباشر مناسبًا للتجربة الأولى أو الإصدارات المبكرة.

## استراتيجية الاختبار والقبول

- اختبارات وحدات لاكتشاف المنصة وHomebrew prefix ومسارات Nginx وPHP دون لمس النظام الحقيقي.
- اختبارات shell للمثبت باستخدام mocks لـ `brew`, `apt-get`, `systemctl`, و`sudo`.
- تشغيل smoke test على macOS Intel وApple Silicon، وعلى Linux الحالي.
- تحقق يدوي من: تثبيت جديد، إعادة تشغيل المثبت، إنشاء plain site، إنشاء WordPress site، start/stop/restart، SSL محلي، backup/restore، Mailpit، وإزالة الأداة.
- يجب ألا يحتوي المسار المشترك على أسماء `systemctl`, `apt-get`, `/etc/nginx/sites-available`, `/run/php`, أو `www-data` إلا داخل adapter خاص بالمنصة أو اختبار مقصود.

## قرارات متروكة للمنفذ

- اختيار تقسيم الملفات النهائي بين `bin/sites`, وحدة Python جديدة، وملفات shell، مع الحفاظ على أقل تغيير ضروري.
- تحديد أسماء حزم Homebrew الدقيقة وإصداراتها من خلال `brew info` وقت التنفيذ.
- اختيار virtualenv ومسار cache المناسبين طالما لا يتم تلويث Python النظام.
- تحديد طريقة readiness checks الدقيقة لكل خدمة.
